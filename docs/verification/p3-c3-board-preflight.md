## 历史布局与默认刷写差异

历史两份 4 MiB 完整恢复件逐字节一致；它们只证明当时状态，不能代替写入当天的新鲜备份。离线解析得到的现有 C3 分区表如下：

| 分区 | 类型 | 偏移 | 长度 |
| --- | --- | ---: | ---: |
| nvs | data/nvs | 0x9000 | 0x6000 |
| otadata | data/ota | 0xf000 | 0x2000 |
| phy_init | data/phy | 0x11000 | 0x1000 |
| coredump | data/coredump | 0x12000 | 0xe000 |
| ota_0 | app/ota_0 | 0x20000 | 0x1e0000 |
| ota_1 | app/ota_1 | 0x200000 | 0x1e0000 |
| base_store | data/nvs | 0x3e0000 | 0x20000 |

历史 bootloader 位于 0x0，镜像格式、芯片、Flash 参数与旧 ota_0 app 可由 esptool image-info 正常识别，镜像哈希有效。历史 otadata 选择 ota_0；ota_1 在镜像起点不具备有效 app 头，不能作为已证明的设备内回退槽。以上是离线备份观察，不宣称写入当天的真实活动槽与安全状态。

独立样例的默认构建配置是单 factory app：生成分区表将 phy_init 放在 0xf000，并将 factory app 放在 0x10000，样例的默认 flash 参数也以 0x10000 写 app。这与现有 otadata、coredump、双 OTA 布局冲突；默认 flash 参数实际写入 0x0 bootloader、0x8000 分区表和 0x10000 app，会覆盖原 bootloader、分区表及 coredump/ota_0 的部分内容，并把原 0xf000 otadata 区域重新解释为 phy_init。它不能用于“不迁分区”的 P3-07 试验。

样例 app 的 954,432 字节小于任一现有 OTA 槽的 1,966,080 字节。离线 image-info 显示其 DROM 映射地址为 0x3c0c0020、IROM 映射地址为 0x42000020；镜像内对应文件段按 64 KiB 页对齐。现有 ota_0、ota_1 的物理偏移也都按 64 KiB 对齐。锁定 IDF 的 bootloader 从实际分区偏移载入镜像，并依据 otadata 选择 OTA 序号。因此，镜像格式与尺寸支持在现有 OTA 槽装载 app 的技术判断，但并不证明旧 bootloader 对最终联网镜像和当次设备安全状态的实际启动结果。

## 单独写 app 的判定

| 候选动作 | 离线判断 |
| --- | --- |
| 只写当前非活动 ota_1 | app 可放入槽内，但历史 otadata 仍选择 ota_0，重启不会运行样例；不能作为 P3-07 实板验证 |
| 只写当前活动 ota_0 | 在当次布局与安全状态保持一致时有技术启动可能，但会覆盖历史唯一已证明可启动的 Base app，失去设备内回退；必须具备同板新鲜双份完整恢复件、ROM 下载模式可用和可执行的物理回刷步骤 |
| 先写 ota_1，再切启动选择 | 可保留原 ota_0 作为回退，但这还需要独立的 otadata 写入、选择/确认和失败处理合同；当前样例没有 OTA 确认入口，不能把它称为“只写一个 app 槽”或直接使用默认 flash 参数 |

旧 bootloader 是否启用自动 OTA 回滚，不能仅从镜像头判定。若后续选择切换 otadata，须先核对旧 bootloader 的实际行为与样例确认路径；不能手工假设试运行会自动确认或回退。

## 写入当天必须重新闭合的条件

1. 重新枚举两板端点，只对目标 C3 核对芯片、MAC、4 MiB 容量、设备原业务身份、端点独占；读取/探测串口可能复位板卡，应记录 boot 变化。
2. 重新读取该 C3 的 bootloader、分区表、otadata、两个 OTA 槽、eFuse 安全状态以及原身份/配置；确认布局、活动槽、候选目标槽、签名/加密/防回滚条件与最终 app 镜像完全匹配。历史离线结论若有变化，重新裁定写法。
3. 在本轮首次覆盖前，取得该板两份完整 Flash 备份，逐字节及摘要一致；将原目标 app 槽和 otadata 的准确恢复范围与步骤绑定到该板。不得跨板使用恢复件，也不得擦除 NVS/base_store。
4. 取得真实受控的实验 Wi-Fi、可达的隔离 TLS Broker、DNS/SAN、CA、独立 ClientID、Topic 和 ACL 输入后，从同一公开源码与固定 SDK 重建最终镜像并核对尺寸、镜像头和摘要。当前没有这些输入的实板验收事实。
5. 选定并获准一个精确写入范围后，写后读回目标范围并比较最终镜像；重启后核对目标 app、原 UUID/配置及 Broker 双侧记录。异常时用同板本轮恢复件回写被改变的 app 槽和 otadata，并读回核对、重启确认原 Base 与身份/配置。若普通启动失败，需有已核对可用的目标 C3 ROM 下载模式和物理接入；不要触碰另一块板。

本轮只做 SDK 安装核对、空输入构建、历史恢复件离线解析和代码检查；未打开串口、未写入设备、未连接真实 Broker。P3-07 的 C3 实板 TLS/ACK/百次回收仍未验收。
